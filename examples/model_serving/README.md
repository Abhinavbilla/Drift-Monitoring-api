# Model-serving drift monitoring example

End-to-end example (Step 3e): a small scikit-learn model trained on Citi
Bike data, served with FastAPI, with its input features logged
asynchronously and periodically sent to the Drift Monitoring API for
analysis.

## Pipeline

1. **`train_model.py`** -- trains a `RandomForestRegressor` predicting
   `trip_duration` from the model's five real input features
   (`pickup_longitude`, `pickup_latitude`, `dropoff_longitude`,
   `dropoff_latitude`, `gender_id`) on `tests/splits/reference_n5000.csv`
   (the Jan-Mar reference sample used throughout this project). Writes
   `artifacts/model.pkl`.
2. **Fit the drift baseline** -- the same five input features (never the
   `trip_duration` target) are fit as the Drift Monitoring API's
   reference, with `decision_mode="calibrated"`. See the worked example
   below.
3. **`serve.py`** -- a separate FastAPI app (its own port, 8001 by
   default) that loads the trained model and exposes `POST /predict`.
   Every prediction's post-preprocessing input features are logged to
   `logs/served_features.jsonl` via a `BackgroundTasks` call, so logging
   never adds latency to the prediction response.
4. **`replay.py`** -- replays a sample of the Apr-Jun production data
   through `serve.py`'s `/predict` endpoint, populating the log.
5. **`scheduled_job.py`** -- reads newly-logged rows, groups them into
   fixed-size windows (**at or above `/fit`'s `recommended_batch_size`**,
   per instruction), and calls `DriftClient.analyze()` for each complete
   window, saving the report to `reports/window_NNNN.json`. Tracks a
   line-count cursor (`logs/.cursor`) so repeated runs (as a real
   scheduled job would make) only process new rows.

## Running it

```bash
# 1. Train the model
python examples/model_serving/train_model.py

# 2. Mint a token scoped to this example's project
python scripts/create_token.py create --email you@example.com \
    --name "model-serving-example" --project model_serving_example

# 3. Fit the drift baseline (with the token from step 2)
python -c "
import sys; sys.path.insert(0, 'clients/python')
from drift_monitor_client import DriftClient
import pandas as pd
df = pd.read_csv('tests/splits/reference_n5000.csv')
features = ['pickup_longitude','pickup_latitude','dropoff_longitude','dropoff_latitude','gender_id']
client = DriftClient('http://127.0.0.1:8000', '<TOKEN>')
result = client.fit('model_serving_example', df[features], calibration_config={'decision_mode': 'calibrated'})
print(result['calibration_info'])  # note recommended_batch_size -- your window size
"

# 4. Start the serving app
python -m uvicorn examples.model_serving.serve:app --port 8001

# 5. Replay production traffic (separate terminal)
python examples/model_serving/replay.py

# 6. Run the scheduled job (window-size from step 3's recommended_batch_size)
python examples/model_serving/scheduled_job.py \
    --project-id model_serving_example --token <TOKEN> --window-size 869
```

## What actually happened, one real run (2026-09-30)

Reference: 5,000 rows -> `/fit` reported `recommended_batch_size=869` for
every continuous feature (KS floor 0.05, alpha 0.05). Replayed 3,000
sampled rows from each of Apr/May/Jun 2016 (9,000 total) through
`/predict`. `scheduled_job.py` processed 8,690 of those rows into 10
complete 869-row windows (310 rows left over, below one window, picked up
by the next run):

| Window | Alert | Drifted feature(s) |
|---|---|---|
| 0 | False | none |
| 1 | False | none |
| 2 | False | none |
| 3 | False | none |
| 4 | **True** | `dropoff_longitude` (D=0.0670, p_adj=0.00975, both gates clear) |
| 5 | False | none |
| 6 | **True** | `pickup_latitude` (D=0.0659, p_adj=0.0122, both gates clear) |
| 7 | False | none |
| 8 | False | none |
| 9 | False | none |

Full per-feature detail (statistic, p-value, adjusted p-value, effect
size vs. floor, decision) is in `reports/window_0000.json` through
`window_0009.json`, committed as real evidence -- not reconstructed after
the fact. Window 4 also shows `gender_id` as `significant=true,
material=false` (PSI-bootstrap p_adj=0.00500, effect 0.048 against a 0.2
floor) -- the same significant-but-not-material pattern characterized at
length in `results/step2_side_by_side.md`, seen here on live traffic
through the actual serving path, not a synthetic validation batch.

`logs/served_features.jsonl`, `logs/.cursor`, and `artifacts/model.pkl`
are regenerated by re-running the pipeline above and are not committed
(see `.gitignore` in this directory) -- `reports/` is the committed,
reproducible evidence of what the calibrated engine actually did.
